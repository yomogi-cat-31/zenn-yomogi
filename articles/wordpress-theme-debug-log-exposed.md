古い WordPress サイトの保守を引き継いで、DB まわりを整理していたときの話です。コードを読んでいて見つけたのは、**申し込みフォームが、申込者の電話番号を含むデバッグ出力を、テーマのディレクトリの中のテキストファイルに追記していて、そのファイルが URL を知っていれば誰でも取得できる**状態でした。

派手な脆弱性ではありません。`var_dump()` の出力をファイルに貯める、という便利な書き方が、そのまま個人情報の公開になっていただけです。ただ、同じ構造の「隙」は、小さなチームで動いている古い PHP サイトにはよくあると思います。この記事では、見つけてから塞ぐまでにやったことと、その過程でついでに見つかった「止まっていたもの」、そこから作ったチェックリストを書きます。

## 1. 何が起きていたか

対象は、WordPress のテーマに申し込みフォームの処理が直接書かれているサイトです。フォームを送ると、テーマ内の PHP が次のことを順に行います。

1. 申込者と社内へメールを送る
2. Slack に通知する
3. 申込者へ SMS を予約する（外部の SMS 配信サービスの API を呼ぶ）
4. 申し込みデータを API 経由で保存する

問題は 3 の SMS の処理でした。2019 年に追加されたコードが、処理の途中経過を `var_dump()` で出力し、それを出力バッファで受け取って、**テーマのディレクトリにあるテキストファイルに `FILE_APPEND` で追記**していました。

```php
ob_start();
var_dump("phone_number : " . $phone_number);
// ... SMS の予約と、API の応答の var_dump ...
$out = ob_get_contents();
ob_end_clean();
file_put_contents(__DIR__ . '/_debug_dump.txt', $out, FILE_APPEND);
```

書き込まれる内容は、申込者の電話番号、受付日時、SMS 配信サービスの応答（電話番号と配信 ID を含む）です。申し込みが 1 件あるたびに 1.5KB ほど増えます。

そしてこのファイルは `wp-content/themes/<テーマ>/sms/_debug_dump.txt` のような場所にあるので、nginx は普通の静的ファイルとして返します。

```sh
$ curl -s -o /dev/null -I -w '%{http_code} %{content_type} %header{content-length}\n' https://example.com/wp-content/themes/<テーマ>/sms/_debug_dump.txt
200 text/plain 184108
```

同じディレクトリには、開発時に手で実行していた `main.php` のようなスクリプトも残っていて、こちらも URL から実行できる状態でした（実行すると、SMS の予約と DB の更新が実際に走ります）。

「リポジトリに入っているファイルは、全部 Web から見える」という当たり前のことが、テーマの中に処理を書いていると忘れられがちです。

## 2. 見つけ方

脆弱性スキャナが見つけてくれたわけではありません。DB の依存をなくす作業のためにコードを読んでいて、`file_put_contents(..., FILE_APPEND)` が目に入り、「このパスは Web から見えるのでは」と思って `curl -I` を打っただけです。

ポイントは **`-I`（HEAD）で確かめる**ことです。中身を取得せずに、ステータスコードとサイズと最終更新日時が分かります。個人情報が入っているかもしれないファイルを、確認のために自分の端末に落とす必要はありません。

```sh
curl -s -o /dev/null -I -w 'http=%{http_code} len=%header{content-length} last-modified=%header{last-modified}\n' <URL>
```

`last-modified` を見れば、「今も書かれているか」も分かります。今回は、テスト申し込みをした時刻と最終更新が一致していて、現役で追記されていることが確定しました。

## 3. 塞いだ順番

対応は、次の順で行いました。順番に理由があります。

### 3-1. まず Web サーバーで拒否する

ファイルを消すのが先ではありません。コードが生きている限り、次の申し込みでファイルは作り直されるからです。先に nginx で、そのディレクトリ以下を外から開けないようにしました。

```nginx
server {
    # ...
    location ^~ /wp-content/themes/<テーマ>/sms/ {
        return 404;
    }
}
```

ここで 1 つ落とし穴があります。**`^~` を付けないと効きません。** WordPress 用の nginx 設定には、たいてい次のような正規表現の `location` があります。

```nginx
location ~ \.php$ {
    fastcgi_pass ...;
}
```

nginx の `location` は、正規表現のものが前方一致のものより優先されます。そのため `location /wp-content/themes/<テーマ>/sms/ { return 404; }` と書いても、`.php` のファイルは `\.php$` のほうに取られて、相変わらず実行できてしまいます。`^~` を付けると「この前方一致が最長で一致したら、正規表現は見ない」になります。

`return 404;` にしたのは、`deny all;`（403）だと「そこに何かある」と分かるからです。好みの範囲ですが、存在を隠したいものには 404 のほうが向いています。

### 3-2. 外から確かめる

設定を反映したら、同じ `curl -I` を流します。対応の前後で同じコマンドを使うと、差分が一目で分かります。

```sh
# 404 になること
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/sms/_debug_dump.txt
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/sms/main.php
# 巻き添えで壊していないこと（200 のまま）
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/style.css
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/
```

ここで「うまくいかなかったこと」を 1 つ。最初に確認したときは 4 つとも 200 で、一瞬焦りました。原因は単純で、設定を反映する前に確認コマンドを流していただけでした。作業をする人と確認する人が別のときは、「どの時点の結果か」を揃えないと混乱します。

もう 1 つ細かい話として、`www` 付きのホスト名からのリダイレクト先が `https://example.com//wp-content/...` とスラッシュ 2 つになるケースがありました。nginx は既定で連続するスラッシュをまとめてから `location` を評価する（`merge_slashes on`）ので問題ありませんでしたが、こういう経路も確認に含めておくと安心です。

### 3-3. ファイルを Web の外へ移す

nginx で塞いだあとに、ファイルを `sudo mv` でドキュメントルートの外へ退避しました。消す前に退避するのは、アクセスログの照合や、例外の出力に DB の接続情報が含まれていないかの確認に使うためです。退避先のパーミッションは `600` にします。

### 3-4. 書き出す処理をなくす

最後に、`var_dump()` をファイルに貯める処理をコードから削除しました。手動実行用のスクリプトと、リポジトリに入っていた 2019 年の出力ファイルも消しました。ここまでやって、初めて「もう作られない」になります。

### 3-5. アクセスログを見る

nginx のアクセスログを、ファイル名で検索しました。

```sh
sudo zgrep -h -E '/sms/(_debug_dump|main)' /var/log/nginx/access.log* | awk '{print $1, $4, $7, $9}'
```

ロードバランサーの配下だと、ログの先頭の IP がロードバランサーのものになっていることがあります。その場合、アクセス元は `X-Forwarded-For` を記録していないと分かりません。これも「引き継いだら確かめること」の 1 つです。

## 4. ついでに見つかった「止まっていたもの」

コードを読みながら対応していると、別のものがいくつも見つかりました。どれも、エラーを握りつぶしていたせいで誰も気づいていなかったものです。

### Slack の通知が 4 年半止まっていた

申し込みの Slack 通知は、トークンを URL のクエリに付けて `chat.postMessage` を GET で呼び、**応答を `@file_get_contents()` で捨てる**作りでした。

```php
@file_get_contents($endpoint . "?token=" . $token . "&channel=" . $channel . "&text=" . urlencode($msg));
```

通知が来ないことに気づいて `auth.test` でトークンを確かめると、2 つあったトークンはそれぞれ `account_inactive` と `token_revoked` でした。発行した人の退職などでトークンが失効し、そのまま 4 年半、誰も気づかなかったわけです。

対応は、Incoming Webhook に切り替えたうえで、**失敗したら必ずエラーログに残す**ようにしました。Webhook は成功すると `ok` を返すので、それ以外は全部記録します。

```php
$res = @file_get_contents(SLACK_WEBHOOK_URL, false, $context);
if ($res !== 'ok') {
    error_log('Slack への投稿に失敗しました: ' . ($res === false ? '応答がありません' : $res));
}
```

`@` で警告を抑えること自体は、URL（= 秘密の値）がログに出ないようにするために残しています。その代わり、結果の判定は自分で行う、という形です。

### 定期実行されているはずの処理が、cron に登録されていなかった

SMS の配信結果を確認するスクリプトがあり、DB には「結果を未確認」のフラグが立った行が大量に残っていました。サーバーの crontab を見ると、そもそも登録されていませんでした。コードがあることと、動いていることは別です。

### 認証情報がソースに直接書かれていた

DB の root パスワード、Slack のトークン、SMS 配信サービスのトークンが、PHP のソースに文字列で入っていました。これらは設定ファイル（WordPress なら `wp-config.php`）の定数に移し、トークンは発行し直しました。**ソースから消しても git の履歴には残る**ので、「消す」と「無効にする」は別の作業です。

移す先の定数は、`defined(...) ||` を付けて定義しておくと、古いコードと新しいコードが混在する瞬間（設定を先に入れて、あとでコードを上げる）にも警告が出ません。

```php
defined('SLACK_WEBHOOK_URL') || define('SLACK_WEBHOOK_URL', 'https://hooks.slack.com/services/...');
```

### README に書いてあるバックアップが、存在しなかった

README には「クラウドの自動スナップショットでバックアップを取っている」とありました。CLI で確認すると、自動スナップショットは設定されておらず、手動のものも 1 つもありませんでした。ドキュメントは、書かれた当時の希望であることがあります。

## 5. 引き継いだら最初に確かめる 6 つのこと

今回の経験を、10 分でできるチェックにまとめます。

1. **ドキュメントルートの下に、ログやデバッグ出力を書いているコードがないか**
   ```sh
   grep -rn -E 'file_put_contents|error_log\(.*, 3,|fopen\(' wp-content/themes/ wp-content/mu-plugins/
   ```
   見つかったら、そのパスを `curl -I` で外から叩く。
2. **公開する必要のないディレクトリ（`sms/`、`scripts/`、`log/`、`tools/` など）が、Web から見えないか**
   nginx なら `location ^~ ... { return 404; }` を足す。`^~` を忘れない。
3. **外部サービスへの通知の失敗が、どこかに記録されるか**
   `@file_get_contents` や `curl_exec` の戻り値を捨てていないか。トークンは `auth.test` のような API で今も有効か。
4. **「動いているはず」の定期処理が、実際に登録されているか**
   `crontab -l`（実行ユーザーも含めて）と、処理の結果のフラグを突き合わせる。
5. **認証情報がソースと git の履歴に入っていないか**
   入っていたら、移すだけでなく発行し直す。
6. **バックアップが「ある」と書かれていたら、本当にあるか**
   コンソールか CLI で、最新のバックアップの日時を見る。

どれも、特別なツールは要りません。要るのは「README とコードを疑って、外から確かめる」姿勢だけです。

## おわりに

今回の問題は、脆弱性スキャンでは出てきません。アプリは正常に動いていて、ファイルは正しく配信されていただけだからです。見つかったのは、たまたま別の目的でコードを読んでいたからでした。

古いサイトを引き継いだとき、機能追加の前に 10 分だけ、このチェックを流してみてください。何も出なければそれでよいですし、何か出たら、それはたぶん何年も前からそこにあります。
