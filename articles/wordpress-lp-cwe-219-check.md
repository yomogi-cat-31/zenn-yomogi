キャンペーンや広告用のWordPress製のLP（ランディングページ）は、短い期間で作ることができ便利なのですが、時折、**ドキュメントルートの下に、見られてはいけないファイルが置かれたまま**になっていることがあります。これはCWEでは **CWE-219: Storage of File with Sensitive Data Under Web Root** に分類されます。

派手な脆弱性ではありませんが、`var_dump()` の出力をファイルに貯める、作業用のスクリプトを置いたままにする、といった開発時の運用が、場合によってはそのまま個人情報の公開に繋がる可能性があります。この記事では、LPでCWE-219が起きやすい理由と典型的なパターン、リポジトリとサーバーの中から確かめる方法、見つかったときの塞ぎ方を紹介します。

## 1. CWE-219 とは

CWE-219 は、「機密情報を含むファイルを、Webサーバーのドキュメントルートの下に置いている」という弱点です。アクセス制御をかけていなければ、URL を知っている（または推測できる）人なら誰でも、そのファイルを取得できます。

## 2. LPで起きやすい理由

- **処理がドキュメントルートの中に書かれる。** WordPressのLPでは、フォームの処理をテーマに直接書くことがあります。テーマのディレクトリはドキュメントルートの下なので、`__DIR__` を基準に書いたファイルは、そのまま Web から見えます。
- **アプリとしては正常に動いている。** エラーも出ず、表示も崩れないので、誰も気づきません。
- **名前が独自の場合、スキャナに引っかからない。** 脆弱性スキャナは `wp-content/debug.log` や `.env` のような、よく知られたパスを当てにいきます。`_debug_dump.txt` のような独自の名前は見つけられません。

## 3. 典型的なパターン

### デバッグ出力をテーマの中のファイルに追記する

例えば、外部 API の呼び出しを調べるために、途中経過を `var_dump()` で出し、出力バッファで受け取ってファイルに追記する、以下のような書き方です。

```php
ob_start();
var_dump("phone_number : " . $phone_number);
// ... API の呼び出しと、応答の var_dump ...
$out = ob_get_contents();
ob_end_clean();
file_put_contents(__DIR__ . '/_debug_dump.txt', $out, FILE_APPEND);
```

このファイルが `wp-content/themes/<テーマ>/doc/_debug_dump.txt` にあれば、nginx は普通の静的ファイルとして返します。仮にこれがフォームの処理の一部だとすると、申し込みが来るたびに、電話番号と API の応答が追記され続けます。

```sh
$ curl -s -o /dev/null -I -w '%{http_code} %{content_type} %{size_download}\n' https://example.com/wp-content/themes/<テーマ>/doc/_debug_dump.txt
200 text/plain 184108
```

### 手動実行用のスクリプトが残っている

開発時に手で実行していた `main.php` のようなスクリプトが同じディレクトリに残っていると、URL から実行できます。ファイルの中身は見えなくても、実行されると外部 API の呼び出しや DB の更新が実際に走ります。

### 配る理由のないファイルがリポジトリに入っている

- なんらかのテキストファイル（`.txt`）
- DB のダンプ（`.sql`）
- 環境変数のファイル（`.env`）やエディタ・OS が作るドットファイル
- 過去に出力されたログ（`.log`）

## 4. 確かめ方

確認は、自分のリポジトリとサーバーの中で行います。リポジトリでは「何が置かれうるか」を、サーバーでは「実際に何が置かれているか」を確かめます。

### 4-1. リポジトリで、機械的に洗い出す

まずは `git` だけで、ドキュメントルートに書き込むコードと、配る理由のないファイルを一覧にします。以下では、ドキュメントルートとして公開されるディレクトリを `app/wp` としています。

```sh
# ドキュメントルートの下に書き込みうるコード
git grep -nE 'file_put_contents|fopen\(|error_log\(.*, *3 *,' -- 'app/wp/*.php'

# 配る理由のないファイル
git ls-files -- app/wp | grep -E '\.(txt|log|sql|bak|env)$|/\.[^/]+$'
```

### 4-2. リポジトリで、コーディングエージェントに読ませる

grepで検知しにくい、「書き込み先を変数で組み立てている」「関数を何段か経由して書き込んでいる」「どこからも呼ばれていない PHP ファイルがある」といった、コードを読まないと判断できないものについては、コーディングエージェントに任せると効率よく調べられます。

```text
このリポジトリのうち、Web サーバーのドキュメントルートとして公開されるディレクトリを特定してください。
その中について、次を一覧にしてください。各項目に、ファイルパスと、機密情報を含みうるかの判断を付けてください。
1. 実行時にファイルへ書き込むコード（file_put_contents, fopen, error_log の第3引数 など）と、その書き込み先。書き込み先が変数の場合は、どこで組み立てられているかまで追ってください
2. 配信する理由のないファイル（.txt, .log, .sql, .env, ドットファイル、手動実行用のスクリプトなど）
3. URL から直接呼び出される想定ではない PHP ファイル
ファイルの変更はしないでください。
```

### 4-3. サーバーで、リポジトリにないファイルを探す

リポジトリにはない、実行時に作られたファイルや、サーバーで手で置いたファイルが存在する可能性もあるので、サーバーの中で、ドキュメントルートを直接確かめます。

```sh
# テーマの下にある、配る理由のないファイル（最終更新日時付き）
sudo find <ドキュメントルート>/wp-content/themes/ -type f \
  \( -name '*.txt' -o -name '*.log' -o -name '*.sql' -o -name '*.bak' -o -name '.*' \) \
  -printf '%TY-%Tm-%Td %TH:%TM  %s  %p\n' | sort
```

リポジトリとの差分を取ると、「リポジトリにないのにサーバーにある」ファイルがはっきりします。

```sh
# サーバー上で、テーマの下のファイル一覧を作る
(cd <ドキュメントルート>/wp-content/themes && find . -type f | sed 's|^\./||' | sort) > server-files.txt

# リポジトリ側で、同じ範囲のファイル一覧を作る
git ls-files -- app/wp/wp-content/themes | sed 's|^app/wp/wp-content/themes/||' | sort > repo-files.txt

# サーバーにだけあるファイル
comm -23 server-files.txt repo-files.txt
```

ビルドで生成されるファイル（webpack の出力など）も差分に出るので、それを除いて残ったものが候補です。

### 4-4. アクセスログで、配信されていないか確かめる

自分のサーバーのアクセスログから、配る理由のない拡張子へのリクエストが 200 で返っていないかを確かめます。

```sh
sudo zgrep -h -E '"(GET|HEAD) [^"]*\.(txt|log|sql|bak|env)[ ?]' /var/log/nginx/access.log* \
  | awk '$9 == 200 {print $7}' | sort | uniq -c | sort -rn
```

`robots.txt` のように公開してよいものも出てくるので、それ以外が候補です。ここで見つかったものは、すでに外から取得されていた可能性があるので、§5-5 のログ調査まで進めます。

## 5. 見つかったときの塞ぎ方

### 5-1. まず Web サーバーで拒否する

先に nginx で、そのディレクトリ以下を外から開けないようにします。

```nginx
server {
    # ...
    location ^~ /wp-content/themes/<テーマ>/doc/ {
        return 404;
    }
}
```

また、nginx設定に、次のような正規表現の `location` がある場合、`^~` を付けないと効きません。

```nginx
location ~ \.php$ {
    fastcgi_pass ...;
}
```

nginx の `location` は、正規表現のものが前方一致のものより優先されます。そのため `location /wp-content/themes/<テーマ>/doc/ { return 404; }` と書いても、`.php` のファイルは `\.php$` のほうに取られて、相変わらず実行できてしまいます。`^~` を付けると「この前方一致が最長で一致したら、正規表現は見ない」になります。

なお、テーマの PHP がファイルシステムから読んでいるファイル（メールのテンプレートなど）は、nginx で拒否しても PHP の処理には影響しません。

#### さらに踏み込むなら、許可リスト方式にする

ディレクトリを1つずつ塞ぐ方法は、見つかったものにしか効きません。テーマの下では「配信してよい拡張子だけを返し、それ以外は 404」にしておくと、名前を知らないファイルも防げます。

```nginx
location ^~ /wp-content/themes/ {
    # 配信してよい静的ファイルだけを返す
    location ~* \.(css|js|map|png|jpe?g|gif|svg|webp|ico|woff2?|ttf)$ {
        try_files $uri =404;
    }
    # それ以外（.txt、.log、.php など）は 404
    return 404;
}
```

`^~` のおかげで、テーマの下の `.php` も `\.php$` の `location` には渡らず、404 になります。WordPress のテーマの PHP は `index.php` から読み込まれるもので、URL から直接呼ばれることは通常ありません。ただし、フォームの送信先がテーマの中の PHP ファイルを直接指している LP もあるので、その場合はそのファイルだけを明示的に `fastcgi_pass` する `location` を足します。導入前に、テーマの PHP を直接指している URL がないかを、アクセスログで確かめておくと安心です。

### 5-2. 外から確かめる

設定を反映したら、同じ `curl -I` を流します。対応の前後で同じコマンドを使うと、差分が一目で分かります。

```sh
# 404 になること
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/doc/_debug_dump.txt
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/doc/main.php
# 巻き添えで壊していないこと（200 のまま）
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/wp-content/themes/<テーマ>/style.css
curl -s -o /dev/null -I -w '%{http_code}\n' https://example.com/
```

### 5-3. ファイルをドキュメントルートの外へ移す

nginx で塞いだあとに、ファイルを `sudo mv` でドキュメントルートの外へ退避します。消す前に退避するのは、アクセスログとの照合や、どんな情報が含まれていたかの確認に使うためです。退避先のパーミッションは `600` にします。

### 5-4. 書き出す処理をなくす

最後に、ファイルに書き出す処理をコードから削除し、手動実行用のスクリプトやリポジトリに入っている過去の出力ファイルも消します。ここまでやって、初めて「もう作られない」になります。ログが必要なら、書き込み先はドキュメントルートの外にします。

### 5-5. アクセスログを見る

公開されていた間に、外から取得されていないかを確かめます。

```sh
sudo zgrep -h -E '/doc/(_debug_dump|main)' /var/log/nginx/access.log* | awk '{print $1, $4, $7, $9}'
```

ロードバランサーの配下だと、ログの先頭の IP がロードバランサーのものになっていることがあります。その場合、アクセス元は `X-Forwarded-For` を記録していないと分かりません。個人情報が含まれていた場合は、ログの結果に応じて、社内の手順に沿った報告が必要になることもあります。

## 6. 確認のチェックリスト

ここまでの内容をまとめたチェックリストを示します。

1. **ドキュメントルートの下に、ログやデバッグ出力を書いているコードがないか**
   `file_put_contents`、`fopen`、`error_log(..., 3, ...)` を `git grep` し、書き込み先がドキュメントルートの外かを確かめる。読み切れないものはコーディングエージェントにも読ませる。
2. **配る理由のないファイルが、リポジトリに入っていないか**
   `.txt`、`.log`、`.sql`、`.env`、ドットファイル、手動実行用のスクリプト。
3. **サーバーに、リポジトリにないファイルが置かれていないか**
   テーマの下を `find` し、リポジトリのファイル一覧と差分を取る。
4. **アクセスログで、配る理由のない拡張子が 200 で返っていないか**
   あわせて、アクセス元（ロードバランサー配下なら `X-Forwarded-For`）が記録されているかも確かめる。
5. **テーマの下が、許可リスト方式で配信されているか**
   少なくとも、公開する必要のないディレクトリ（`doc/`、`scripts/`、`log/`、`tools/` など）は `location ^~ ... { return 404; }` で塞ぐ。`^~` を忘れない。

## おわりに

CWE-219は、アプリは正常に動いていて、独自の名前のファイルが正しく配信されている状態なので、仕込まれたまま引き継いだりした場合、見つけづらい側面があります。

WordPress製のLP環境をお持ちの方はぜひ一度、確認してみてください。
